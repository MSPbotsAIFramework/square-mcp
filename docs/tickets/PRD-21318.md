## Product design

### Goals / Non-goals

**Goals:**
- Ship a first version of a Square MCP connector in `MSPbotsAIFramework/square-mcp` that lets an Agent (through the MSPbots Connector gateway, or any MCP client pointed at this service) read a connected Square seller's core business data — locations, customers, catalog items, orders, and payments — and current inventory counts, and issue a refund against a completed payment, using a Square access token supplied per request (never stored by this service).
- Match the shape, isolation model, and documentation conventions already established by this org's other first-generation vendor-mcp connectors (the sibling pattern), so this connector is operable, reviewable, and extensible the same way the others are.
- Cover enough of Square's surface (7 resource areas, 12 tools) that the connector is independently useful on its own — not a stub that only proves the pipe works.

**Non-goals (v1):**
- Does not implement Square's OAuth authorization-code flow inside this service. `vendor-register` only supports plain header-credential vendors (no OAuth support); this connector takes a pre-obtained Square access token (Personal Access Token, or an OAuth token a tenant already has) as a request header, the same "bring your own token" pattern the sibling pax8 connector uses. Implementing OAuth token exchange/refresh would require persisting per-tenant state, which conflicts with the stateless, request-isolated run model (SOP §3).
- Does not implement Square webhooks (real-time event push). Webhooks need a public callback endpoint; this service is not exposed to the public internet and only accepts calls from the Gateway (SOP run model), so there is no way to receive a Square-initiated callback here. Flagged as a possible separate ticket if real-time notifications are ever wanted, likely on the gateway side rather than in this repo.
- Does not cover Square's Team/Labor, Loyalty, Gift Cards, Subscriptions, or Invoices APIs. The ticket's one-line ask is "give live access" to the business generically, with no specific capability named beyond that; the 7 areas selected (Locations, Customers, Catalog, Orders, Payments, Refunds, Inventory) are the core "run a POS / look at the money" surface. Adding the rest is a natural v2 and should be a new ticket once there is a real ask for it (YAGNI — a 20-tool cap exists for a reason, SOP §2).
- Does not add catalog/customer/order **create or update** tools, or void/cancel endpoints. The only write/destructive tool in v1 is `square_create_refund`, chosen because "issue a refund" is one of the most common POS actions an assistant would be asked to do and Square's refund endpoint is a single, well-bounded, idempotent call. Broader write access is deferred.
- Does not implement the platform's "credentials encrypted" and "every action logged" promises as code in this repo — those are Connector-gateway features (README "MSPbots Connector" section, "Visibility"/"Security" rows: per-record credential encryption and per-call audit logging are done by the gateway/platform, not by individual vendor MCP services). This repo's job is to never log or persist the credential it is handed (AC-level requirement below), not to implement encryption or an audit log itself.

### Acceptance criteria AC1..AC24

**Access, environment, and transport**

- **AC1** — Given a valid `X-Square-Access-Token` header on a `/mcp` request, when any tool is called, then the service forwards `Authorization: Bearer <token>` to Square and does not read, require, or fall back to any server-side stored credential (env var) for that call.
- **AC2** — Given no `X-Square-Access-Token` header, when a `tools/call` request is sent to `/mcp`, then the service responds `401` with a body listing the required header(s), and makes no outbound call to Square.
- **AC3** — Given `X-Square-Environment: sandbox`, when any tool is called, then the outbound request goes to `https://connect.squareupsandbox.com/v2`; given the header is omitted or set to `production`, outbound requests go to `https://connect.squareup.com/v2`.
- **AC4** — Given `X-Square-Environment` set to any value other than `production` or `sandbox`, when any tool is called, then the tool returns an `invalid_argument` error and makes no outbound call.
- **AC5** — Given two concurrent `tools/call` requests carrying two different `X-Square-Access-Token` values (and possibly different `X-Square-Environment` values), when both run at the same time, then each call's outbound Square request carries only its own token and base URL; neither leaks into the other.
- **AC6** — Given a `GET /health` request, when the service has no Square credential configured anywhere, then it still returns `200 {"status": "ok", ...}` — health does not depend on reaching Square.
- **AC7** — Given a `tools/list` call sent with no prior `initialize` session (no session id), when the request is well-formed, then it succeeds with `200` (Streamable HTTP stateless mode, SOP §1.3) — the service holds no session state.

**Locations**

- **AC8** — Given a valid credential, when `square_list_locations` is called, then it calls `GET /v2/locations` and returns the seller's locations (at minimum `id`, `name`, `status` per location).

**Customers**

- **AC9** — Given a valid credential, when `square_list_customers` is called with no arguments, then it calls `GET /v2/customers` and returns a page of customers plus a `cursor` for the next page when more results exist.
- **AC10** — Given one or more of `phone_number`, `email_address`, `given_name`, `family_name`, when `square_search_customers` is called, then it calls `POST /v2/customers/search` with a filter built from exactly the fields provided, and returns the matching customers.
- **AC11** — Given a `customer_id` that exists, when `square_get_customer` is called, then it calls `GET /v2/customers/{customer_id}` and returns that customer's detail.
- **AC12** — Given a `customer_id` that does not exist, when `square_get_customer` is called, then it returns a `not_found` error envelope, not an unhandled exception.

**Catalog**

- **AC13** — Given a valid credential, when `square_list_catalog_items` is called, then it calls `GET /v2/catalog/list?types=ITEM` (with `cursor` when provided) and returns catalog items.
- **AC14** — Given an `object_id` that exists, when `square_get_catalog_item` is called, then it calls `GET /v2/catalog/object/{object_id}` and returns that object; given an `object_id` that does not exist, it returns `not_found`.

**Orders**

- **AC15** — Given `location_ids` and optional `state`/date filters, when `square_search_orders` is called, then it calls `POST /v2/orders/search` with a body built from exactly the filters provided, plus `cursor` when provided, and returns matching orders.
- **AC16** — Given an `order_id` that exists, when `square_get_order` is called, then it calls `GET /v2/orders/{order_id}` and returns that order; given one that does not exist, it returns `not_found`.

**Payments**

- **AC17** — Given optional `location_id`/`begin_time`/`end_time`/`cursor`, when `square_list_payments` is called, then it calls `GET /v2/payments` with exactly the query parameters provided and returns the page of payments.
- **AC18** — Given a `payment_id` that exists, when `square_get_payment` is called, then it calls `GET /v2/payments/{payment_id}` and returns that payment; given one that does not exist, it returns `not_found`.

**Inventory**

- **AC19** — Given a `catalog_object_id` (and optional `location_ids`), when `square_get_inventory_count` is called, then it calls `GET /v2/inventory/{catalog_object_id}` (with `location_ids` as a query filter when provided) and returns the current stock counts per location.

**Refunds (the one write/destructive tool)**

- **AC20** — Given a `payment_id`, an `amount`, a `currency`, and no `idempotency_key`, when `square_create_refund` is called, then the service generates an idempotency key, calls `POST /v2/refunds`, and returns the created refund (`id`, `status`, `amount_money`).
- **AC21** — Given the same `idempotency_key` is supplied on two separate calls to `square_create_refund` with the same arguments (simulating a client-side retry), when both are executed, then Square returns the same refund (idempotent), and the tool does not treat the second call as a new refund.
- **AC22** — Given Square rejects the refund request (e.g. amount exceeds the refundable balance, payment already fully refunded), when `square_create_refund` is called, then it returns a structured error with Square's upstream code/message surfaced, not an unhandled exception.

**Cross-cutting error handling and docs**

- **AC23** — Given any Square 4xx/5xx response on any tool, when the tool runs, then the error is mapped to the structured envelope `{"error": {"code", "message", "retryable"}}` with `code` drawn from the fixed vocabulary (`unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error`), never an unhandled exception; for `429` or `5xx` on idempotent read calls, the service retries with backoff honoring `Retry-After` before giving up.
- **AC24** — Given the README's "Tool List" table, when this ticket is done, then it lists all 12 tools with a description and key parameters in the sibling-pattern shape, and "Authentication headers" documents `X-Square-Access-Token` (required) and `X-Square-Environment` (optional, default `production`).

## Tech design

### Conclusion

Build `square-mcp` from scratch as a Python 3.12 / `uv` / FastMCP Streamable-HTTP service, structured exactly like the sibling `pax8-mcp` (one `SquareClient` wrapping `httpx`, one `tools/<resource>.py` module per resource, `contextvars`-based per-request credential middleware, multi-stage Docker image). Scope for v1 is 12 read-mostly tools across 7 resource areas (Locations, Customers, Catalog, Orders, Payments, Inventory, Refunds), with one destructive tool (`square_create_refund`). Unlike the sibling connector's legacy plain-string error convention (a pre-existing, already-flagged gap in that repo), this brand-new repo implements the SOP §4 structured error envelope from the start, since there is no existing convention here to stay consistent with.

### Decisions made by DEV01 (SOP §2.4 — no one to ask, first version)

- **Picked these 7 resource areas / 12 tools for v1** (Locations, Customers, Catalog, Orders, Payments, Inventory, Refunds) instead of covering Square's full surface. Why: the ticket's ask is generic ("live access" to the business), so scope had to be chosen rather than specified; these are the areas every Square business has and that an assistant would plausibly be asked about (where's my shop, who is this customer, what does this item cost, what happened in this order, did this payment settle, how much refund can I give, how much stock is left). Alternative considered: cover Team/Labor, Loyalty, Gift Cards, Subscriptions, Invoices too in one pass — rejected as over-scoping a first version (SOP §2 caps a service at ≤20 tools; the 12 chosen already approach that once headroom for v2 is considered) and as a YAGNI violation with no concrete ask behind it.
- **Did not add catalog/customer/order create-or-update tools.** Why: none of the ticket text or Square's docs makes a specific write ask beyond "access"; adding writes widens the blast radius (SOP's caution to only accept explicit resource IDs, never fuzzy/batch deletes or updates) without a driving requirement. The one write tool kept (`square_create_refund`) is the exception, justified below.
- **Chose `square_create_refund` as the only v1 write tool.** Why: refunding is one of the most common POS assistant actions, Square's refund endpoint is a single well-bounded idempotent call (unlike, say, creating an order, which involves line items, taxes, and discounts with many edge cases), and it is the only Square write endpoint that ships with a first-class idempotency mechanism (`idempotency_key`) matching this connector's safety requirements out of the box.
- **Credential is a single bearer token header, `X-Square-Access-Token`**, carrying either a Square Personal Access Token or a pre-obtained OAuth access token — not an OAuth flow implemented in this service. Why: matches the sibling `pax8-mcp` pattern (`X-Pax8-Token`) and the only auth mode `vendor-register` supports; alternative (full OAuth) rejected per Non-goals above (needs persistent per-tenant state).
- **Added an optional `X-Square-Environment` header** (enum `production` | `sandbox`, default `production`) to pick Square's base URL per request. Why: Square Sandbox is the only way to exercise this connector without a live Square business — including DEV01's own automated tests — and it costs one optional header with a safe default; it is not a secret, so it is modeled as a plain enum header rather than a `credential_fields` entry.
- **Pinned `Square-Version` to a server-side constant** (`2024-07-17`, overridable via `SQUARE_API_VERSION` env var, never an agent-supplied header). Why: the API version controls the response shapes this code parses; letting a caller choose it would let a caller silently break parsing. This follows the same non-secret, server-config pattern as `PAX8_BASE_URL` in the sibling repo.
- **Structured error envelope from day one** (`{"error":{"code","message","retryable"}}`, SOP §4) instead of the sibling repo's plain `"Error {code}: {message}"` strings. Why: the sibling's plain-string convention is a pre-existing, already-flagged gap in that repo (see its own PRD-21599 "Reuse & cleanup" — "recommend a follow-up ticket to migrate ... to the structured envelope"); a brand-new repo has no existing convention to stay consistent with, so it should start from the SOP's actual spec rather than copy a known gap forward.

Nowhere — `square-mcp` is an empty repository (`README.md` only, `0aa8aea`). Everything in the Change list below is new. The sibling `pax8-mcp@master (2f5137b)` is cited throughout as the structural pattern being reused, not as code being changed.

### Option analysis

- **Mirror the sibling `pax8-mcp` structure exactly** (chosen) vs. inventing a new layout. Rejected inventing one: the org already has a working, reviewed shape (contextvars middleware, one client + one tools-module-per-resource, the same test layout); diverging would make this connector harder to review and maintain relative to its siblings for no benefit.
- **One `tools/<resource>.py` module per Square resource** (`locations.py`, `customers.py`, `catalog.py`, `orders.py`, `payments.py`, `inventory.py`, `refunds.py`) (chosen) vs. one flat `tools.py` with all 12 functions. Chosen per-resource split: matches the sibling pattern exactly (it splits by resource, not by read/write — see its own design notes) and keeps each file's diff small when a later ticket touches one resource.
- **Structured error envelope** (chosen, see Decisions above) vs. copying the sibling's plain-string convention for consistency with "how connectors look today." Rejected copying: SOP §4 is the actual spec; the sibling's shortcut is explicitly flagged as tech debt in its own design doc, not a pattern to propagate.
- **Idempotency key auto-generated when the caller omits one** (chosen, `uuid4()` per call, stable across any transport-level retry of that same call) vs. requiring the caller to always supply one. Chosen auto-generate: an Agent calling this tool from natural language has no reason to think about idempotency keys; Square only needs the key to be unique per logical refund attempt, and this service can guarantee that itself while still accepting a caller-supplied key for callers that want to control retries explicitly (needed for AC21).
- **Retry only idempotent (read) calls on `429`/`5xx`** (chosen) vs. retrying all calls including `square_create_refund`. Chosen read-only auto-retry: a `POST /v2/refunds` call is only safe to retry because of the idempotency key, and this design already guarantees the key is stable per logical call — but to keep the retry policy simple and auditable, v1 does not add transport-level auto-retry to the refund path; a failed refund call surfaces the error and leaves retrying (with the same key, safe by construction) to the caller. This avoids any ambiguity about whether a "successful-looking timeout" already created a refund.

### Data & API contract

### Key flow / sequence

1. Agent/client sends `tools/call square_create_refund {...}` over `/mcp`, carrying `X-Square-Access-Token` (and optionally `X-Square-Environment`).
2. `GatewayCredentialMiddleware` reads both headers into their `contextvars.ContextVar`s.
3. `client_factory()` resolves a fresh `SquareClient(access_token, environment)`; an invalid `environment` value short-circuits here with `invalid_argument` (AC4) before any HTTP call.
4. The tool resolves (or generates) `idempotency_key`, builds the refund body, calls `client.post("/refunds", json_body={...}, idempotency_key=...)`.
5. `SquareClient` sends `POST`, maps any non-2xx to `SquareError` via the fixed code vocabulary.
6. Tool returns either the JSON-encoded refund, the `401` (missing header, handled one layer up), or the `{"error": {...}}` envelope.

### Non-functional

- **Multi-tenant isolation**: per-request `contextvars` only, no global/module-level credential state — same mechanism as the sibling connector (AC5).
- **Idempotency / safety**: `square_create_refund` always carries an idempotency key (caller-supplied or server-generated), so a retried call with the same key cannot double-refund (AC21); `destructiveHint=True` (irreversible money movement), `idempotentHint=True`, `readOnlyHint=False`. All 11 other tools are `readOnlyHint=True`. This satisfies Micus's Done-when #3 in full: the "held by supervised mode / approvals like any other write tool" half of that criterion is a platform/gateway behavior triggered purely by `destructiveHint=True` (same mechanism every other connector's write tools already go through) — this connector does not need to implement an approval gate itself, only to set the annotation correctly, which it does.
- **Performance / token economy**: all `list`/`search` tools accept `cursor` and return Square's native page size (Square's own default/limits apply; this connector does not invent a separate cap) — a later ticket can add an explicit `limit` clamp if a real token-budget problem shows up; responses are serialized compactly (`ensure_ascii=False`, no `indent=2`) and only the fields a caller is likely to need are kept (ids, human-readable names/amounts/statuses), not the full raw Square object, to keep tool-call responses token-economical per SOP §2.
- **Network robustness**: 5s connect / 30s read timeouts, retry-with-backoff honoring `Retry-After` on `429`/`5xx` for read calls (AC23), single call capped under ~120s total (SOP §5).
- **Security**: credential handling is Header-only, per-request, never logged or persisted (goes with the platform's "credentials encrypted" promise — this service simply never stores anything to encrypt); no credential value appears in any log line, error message, or test fixture beyond a placeholder.
- **Logging/observability**: no request/response bodies logged (refund amounts and customer PII can appear in them); tool-call-level audit logging is a platform/gateway concern per the README's own "Visibility" section, not duplicated here.

- **Rollout**: first version — merged to `main`, then registered via `/api/vendor-register` (not `/api/deploy-int`, since the gateway does not know this vendor yet) in the review leg. No existing tenant or Agent flow is affected (nothing currently calls this connector).
- **Rollback**: if the first INT deployment misbehaves, there is nothing to roll back to except "not registered" — the review leg would report the registration/deploy result as failed and this ticket returns to `blocked` rather than a code rollback, since there is no prior working version to redeploy.

### Effort & breakdown

Story points: 5 (product decision: build as one ticket, not split — see below)
Tier: new subsystem — a brand-new MCP server (not a modification), 7 distinct external-API resource areas with different response shapes to map and test, one destructive/idempotent write operation, and ~24 acceptance scenarios; per `mcp-track.md` §2.5b, new MCP repos generally land at 3 or 5, and the combination of "new build," "external API entirely unknown to this org," "one destructive write," and the breadth of resource areas (well above a single-tool or single-resource first version) puts this at the top of that range rather than the middle.

## Test cases
